# LCD-Bootloader nach Z13 · LCD bootloader after Z13

**Deutsch.** Der installierte Z13 ist die Referenz. Ein separat gebauter Laborstand schließt eine Lücke in der DFU-Anzeige. Falls die Ereigniswarteschlange voll ist, holt die Hauptschleife die zuletzt gültige Anzeige beziehungsweise das Aufräumen nach dem letzten Ereignis nach. „Ready“ bedeutet, dass der Transport verbunden ist. „Receiving…“ kennzeichnet den gestarteten DFU-Vorgang. Die Anzeige schätzt weder einen Prozentwert noch meldet sie einen erfolgreichen Neustart. Ein Firmwareupdate der Anwendung benötigt diesen Laborstand nicht.

Für das gleiche LCD-Ziel sinkt die Größe von 28.344 auf 26.452 Byte. Die freie Bootregion wächst von 328 auf 2.220 Byte. Der Build verlangt mindestens 1.024 Byte Reserve einschließlich der Initialwerte für den RAM. Die zwei unabhängigen Builds liefern bytegleiche BIN-, Intel-HEX- und ELF-Dateien. Zwei absichtlich zu große Builds wurden abgewiesen. Die Anwendung erhält durch die freie Bootregion keinen zusätzlichen Speicher.

Der DFU-Einstieg per rechter Taste behält die zwei Abfragen von Z13. Beim Einschalten rechts bis durch die zweite Abfrage halten (rund drei Sekunden bei durchgehendem Druck). Frühes Loslassen ohne erneuten Druck startet bei gültiger Anwendung regulär. Auch ein erneuter Druck vor der späteren Abfrage kann den Rettungseinstieg auslösen. Der Anwendungsbefehl über GPREGRET bleibt verfügbar. Eine fehlende oder ungültige Anwendung löst den DFU-Pfad vor der Tastenentscheidung aus.

Der Kandidat hat keine DFU-Signatur und keinen veröffentlichten Updatezähler. Quellen, Linker-Map, ELF, Rohabbild und Tests sind Material für die technische Prüfung. Die Funkübertragung, die optische Anzeige, der Neustart nach Flashunterbrechung und das Wiederherstellen per SWD sind für den Kandidaten physisch offen. [Prüfwerte](BL_Pruefstand_Evidence.json)

**English.** Z13 is the installed reference. A separate bench candidate retries the latest DFU display update or terminal display teardown in the main loop after a full SDK event queue. “Ready” denotes a connected transport. “Receiving…” denotes DFU start. The UI provides neither byte progress nor confirmation of a successful reboot. App-only updates do not require this bootloader.

The LCD image shrinks from 28,344 to 26,452 bytes, leaving 2,220 bytes in the boot region. The linker enforces 1,024 bytes of headroom including RAM initializers. Two builds produced identical BIN, Intel HEX and ELF. Two oversize controls failed as intended. The two-stage right-button check, including the late recovery entry, is retained. No candidate OTA signature or release counter has been issued. Real-device BLE, display, interrupted update and SWD recovery acceptance remain pending.
